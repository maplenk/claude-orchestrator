Orchestrator Setup

A plan → delegate → verify workflow where implementation reaches the tree only through delegated agents, and roles run on whichever model you choose.

4 harnesses3 roles2 output stylesMIT

What it is

Two ideas do most of the work. Roles and harnesses are orthogonal — a role is the job, a harness is the model executing it, so one role definition runs on Claude, Codex, Grok or pi with no per-model copies. And the no-implement rule is enforced, not requested — a hook blocks source edits in the main session while orchestrator mode is on, so a wave can only reach the tree through an agent that was independently verified.

Nothing activates until you select the output style. Under any other style the guard, the workflow, and the harness prompt are all inert.

Install

Steps 1–3 are required. Step 4 is what turns the mode on.

  1. Add the marketplace and install

    /plugin marketplace add maplenk/claude-orchestrator
/plugin install orchestrator@orchestrator-marketplace

    Type these — they're slash commands, not shell.

  2. Restart the session

    A SessionStart hook symlinks five tools into ~/.claude/bin/. Plugin file bodies don't get ${CLAUDE_PLUGIN_ROOT} expanded, so the role definitions need a stable path to point at. Until the hook has run, those paths don't exist.

  3. Check the wiring

    /orchestrator:setup
# or directly:
~/.claude/bin/orchestrator-doctor

    Every non-passing check prints the exact command that fixes it.

  4. Turn the mode on

    /config → Output style → Orchestrator

    Then /orchestrate <goal>. Output style is read once at session start, so it takes effect on the next session or after /clear.

A first run typically shows two warnings: the output style not yet selected, and the bus not registered as an MCP server. Both are one command each.

Harnesses

Only claude is required. Each additional harness buys one more independent model family — which matters because re-delegating a failed task to the same model usually reproduces the same mistake.

Every model runs in its own CLI — never Claude Code wearing another model's name — so each applies its own context and output limits.

HarnessRunsNeedsCompanion plugin
claudeAgent toolNothing — built in. The only harness with native worktree isolation.—

The plugins are optional but worth having: they add background job control, review commands, and status/result/cancel. Use those for reviews; use run-role when you need one of your role definitions driving the model.

Roles × harnesses

Pick the role by what the task is, then the harness by which model should run it. A second independent attempt is the same role on a different harness — never a different role.

RoleJobOn claudeElsewhere
developerScoped implementorAgent(orchestrator:developer)run-role developer --harness X
ui-developerFront-end, a11y, design systemAgent(orchestrator:ui-developer)run-role ui-developer --harness X
verifierEvidence-driven checkAgent(orchestrator:verifier)run-role verifier --harness X

Plugin agents are namespaced, so the Agent tool needs orchestrator:<role>. run-role takes the bare name — it resolves role files, not registered agent types, and checks your own ~/.claude/agents/ first so you can override a packaged role without editing the plugin.

The role reaches each CLI by flag — -c model_instructions_file= for codex, --rules for grok, --append-system-prompt for pi — so nothing is written into your workspace and worktrees stay cleanly removable.

Add --worktree to give a task its own checkout. It prints the branch, the base SHA it cut from, and the merge and cleanup commands. It is opt-in: where an agent's work lands is your decision, not a silent default.

--read-only is refused except on pi. Only pi's --tools read genuinely removes the write tools. codex's sandbox governs shell commands but not its own patch tool, and grok's tool denylist leaves other paths open — both were verified writing the target file anyway. A flag that reports success and enforces nothing is worse than no flag, so run-role refuses rather than pretending.

Model choice belongs to the role × harness pair. harnesses.json takes a modelByRole map — pi runs Kimi for ui-developer and DeepSeek for everything else.

The dashboard

The bus serves a live control plane at http://127.0.0.1:8477/ — the same port, no extra process.

It shows the current wave and its four stages, runs with their real durations and outcomes, the doctor's checks with a copyable fix beside each, the harnesses you can delegate to, registered agents, and the message feed. Every figure traces to an API field: the success rate reads as a fraction of closed runs rather than a percentage, and nav entries with no backing data say NOT YET rather than showing invented numbers.

Pause is real — it sends SIGSTOP to the run's process and SIGCONT to resume. Safe for a breather; a process frozen mid-request to a model API may have its socket time out, so do not pause for an hour.

Theme is explicit: Light, Dark or System, persisted. The page is re-read from disk on every request, so if you are editing it the next refresh shows your change with no restart.

Messaging

SendMessage reaches Claude agents only. Codex, grok and pi are headless CLI processes with no mailbox — messages to them vanish with no error. So the plugin ships a bus that both sides can reach.

claude mcp add agent-bus --transport http http://127.0.0.1:8477/mcp

Claude agents get chat_register, chat_send, chat_read, chat_wait, chat_who. Headless harnesses use the same operations over REST on the same port. Both write one JSONL log per branch, readable with agent-board whether or not the server is up.

Register it before you need it. MCP servers connect at session start. A bus started mid-session is reachable over REST only — which is why the port is fixed rather than ephemeral.

When something is wrong

A plugin installs but reports “couldn’t be loaded”

Check its .claude-plugin/plugin.json for "hooks": "./hooks/hooks.json". That path is loaded automatically; naming it again makes the loader resolve the same file twice and reject the entire hooks block.

The plugin's skills and agents still load, so the failure is easy to miss — but none of its hooks run. Remove the key. The doctor flags this across every installed plugin.

Edits to the repo don’t take effect

Installing from a local path copies the repo into the plugin cache, and /reload-plugins won't re-copy while the version is unchanged. Either bump version in plugin.json, or sync the cache directly:

rsync -a --delete --exclude='.git' ./ \
  ~/.claude/plugins/cache/orchestrator-marketplace/orchestrator/0.1.0/
Delegated agents can’t write anything

The guard exempts subagents by agent_id, but a run-role harness is a top-level session and has none — so it looks exactly like an orchestrator. run-role marks its process tree with ORCHESTRATOR_DELEGATE and the guard exempts on that.

If you see denials in a delegated agent's log, check that variable survived into its environment. Native CLIs sidestep it entirely — codex, grok and pi are not Claude Code, so no hook fires for them at all.

The guard isn’t blocking edits

It only acts when the output style is exactly Orchestrator, and it deliberately ignores any tool call carrying an agent_id — subagents are the implementors and must be able to write.

Output style is read once at session start. If you just selected it, start a new session or /clear.

Plugin output styles are stored namespaced as orchestrator:Orchestrator. A check comparing against the bare name never matches, and the guard then enforces nothing while appearing healthy. orchestrator-doctor reports the real value it found, so if enforcement seems absent, read that line rather than trusting the style picker.

A pi run takes minutes, or times out

Expected. Observed runs have exceeded four and seven minutes on small tasks. Delegate in the background rather than raising timeouts, and lower RUN_ROLE_THINKING if you need faster turnaround.

An agent claims it messaged another and nothing arrived

Almost certainly SendMessage aimed at a headless harness. Use the bus. On the bus, identity is issued rather than claimed — register returns a token and the server stamps the sender itself, so a forged from field is ignored rather than trusted.
